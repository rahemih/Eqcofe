# MA-POSTMERGE-VERIFY-SUPPRESSED-001

## Status

OPEN — REMEDIATION IN PROGRESS

## Summary

The first post-bootstrap canonical merge, PR #172, was merged correctly by the deterministic `Merge Policy Enforcement` workflow through `workflow_dispatch`. The merge executor revalidated all required gates and merged exact PR head `108b84481e11c76292e60213cf403688ef577517` as canonical merge commit `deb78949fc289ce5d530f99ed2f6da62a89785f5`.

After the merge, no `push`-triggered `Canonical CI` or `Phase A Verification` workflow run was created for the exact merge commit, even though both workflows are configured to run on pushes to `main`.

This means the merge itself is valid, but the established exact-canonical-main post-merge verification control was not executed. `NOT_EXECUTED` is not treated as `PASS`.

## Evidence

- Canonical merge workflow run: `34954608475` — SUCCESS.
- Merge job: `104333521662` — SUCCESS.
- Merge executor output: `status=MERGED`, PR `172`, SHA `deb78949fc289ce5d530f99ed2f6da62a89785f5`.
- PR #172: merged=true.
- `main` HEAD after merge: `deb78949fc289ce5d530f99ed2f6da62a89785f5`.
- Query for Actions runs on the exact merge SHA returned zero runs immediately after merge.
- PR #152 previously established that Phase A must execute on the exact canonical `main` head rather than reuse PR-head evidence.

## Root cause

CONFIRMED PLATFORM BEHAVIOR.

The deterministic merge job authenticates with the repository `GITHUB_TOKEN`. GitHub prevents most events generated by actions authenticated with `GITHUB_TOKEN` from recursively creating new workflow runs. Therefore the merge-generated `push` event does not create the configured push-triggered Canonical CI and Phase A runs.

This is not a Ruleset bypass and did not invalidate PR #172's pre-merge gates. It is a post-merge observability / verification regression introduced by the transition from manual bootstrap merge to the canonical GitHub-Actions merge executor.

## Impact

- PR #172 merged through the intended deterministic path.
- Exact-head pre-merge `merge-policy`, `verify`, and `phase-a` all passed.
- The merge commit tree equals the reviewed PR-head tree, but the historically required post-merge CI execution on exact canonical `main` did not occur.
- Future canonical merges would repeat this gap if no remediation is made.

## Immediate containment

- Do not treat missing post-merge workflows as PASS.
- Do not relax Ruleset required checks.
- Do not return to manual Owner merge or Bootstrap Exception.
- Hold PR #171 and Item 7 progression until a canonical remediation exists.

## Remediation design after review

Task: `MA-POSTMERGE-VERIFY-001`.

The canonical merge workflow is split into three responsibilities:

1. `merge` — revalidates policy, performs the merge and resolves the exact canonical `merge_commit_sha`;
2. `postmerge-verify` — runs on a separate GitHub-hosted `ubuntu-latest` job with `contents: read` only, checks out exactly that immutable merge SHA from `github.repository`, persists no Git credential, then runs full `pnpm verify` and Phase A;
3. `postmerge-failure` — runs only when merge succeeded but verification did not succeed, has `issues: write` only for reporting, and creates/reuses an Owner-assigned investigation issue with `incident_state: POST_MERGE_FAILED`.

### SQ-1 — Checkout source

- The merge SHA is resolved from `repos/${GITHUB_REPOSITORY}/pulls/${PR_NUMBER}` after the merge.
- The SHA must be a full 40-hex value.
- The workflow additionally resolves `repos/${GITHUB_REPOSITORY}/commits/${merge_sha}` before publishing the job output.
- The verification checkout explicitly uses `repository: ${{ github.repository }}` and `ref: ${{ needs.merge.outputs.merge_sha }}`.
- It never uses a fork repository, moving `main`, or PR-head ref for post-merge verification.
- External PR-head repositories remain fail-closed in the canonical Merge Policy Controller before merge and are covered by its existing dedicated test.

### SQ-2 — Isolation / sandbox truth

The verification job uses a separate GitHub-hosted `ubuntu-latest` runner. It is isolated from the merge job and receives only `contents: read` repository permission. Both the pre-merge and post-merge checkout steps use `persist-credentials: false`.

This task does **not** claim a no-code-execution sandbox. `pnpm install`, `pnpm verify`, and Phase A intentionally execute the already-reviewed canonical repository code. The runner workspace is writable and this workflow does not impose an outbound-network firewall. The security control is therefore least-privilege credential isolation plus an ephemeral hosted job, not a false claim that malicious code could never execute.

No PAT and no GitHub App token are introduced by this remediation.

### SQ-3 — Failure mode

If merge succeeds but exact-SHA post-merge verification is not successful:

- the workflow remains non-success / fail-visible;
- `postmerge-failure` creates or reuses an issue titled with the PR number and exact merge SHA;
- the issue records `incident_state: POST_MERGE_FAILED` and is assigned to the repository owner;
- automatic rollback is prohibited;
- rollback or further remediation requires a separate governed investigation/task and normal gates.

`POST_MERGE_FAILED` is an incident outcome marker, not a silent expansion of the frozen workflow/task state machine.

### SQ-4 — Race safety

The verifier consumes only the immutable `needs.merge.outputs.merge_sha`. If PR A merges as `SHA_1` and `main` later advances to `SHA_2`, PR A's verifier still checks out and verifies `SHA_1`. A later canonical merge has its own workflow execution and its own merge output. The workflow-contract test explicitly rejects moving `main`, `github.ref`, `github.sha`, and PR-head references in the post-merge verification job.

### SQ-5 — Credentials

- Merge job: per-run GitHub Actions `GITHUB_TOKEN`, `contents: write`, `pull-requests: write`, `issues: read`; no persisted Git credential.
- Post-merge verification job: `contents: read` only; no explicit `GITHUB_TOKEN` environment binding; checkout uses `persist-credentials: false`.
- Failure reporter: separate job with `contents: read` + `issues: write`; token is exposed only to the reporting command and that job does not checkout or execute repository code.
- No PAT, persistent repository token, or GitHub App credential is stored or introduced.
- GitHub generates the workflow token per run; project-level manual rotation is therefore not used for this credential type.

### Timeout

- Merge job: 10 minutes.
- Post-merge verification job: 30 minutes.
- Failure reporter: 5 minutes.

A non-success verification result after a successful merge is routed to the failure reporter. Manual cancellation of an entire workflow remains an operational condition that must be visible in Actions history and investigated if post-merge evidence is incomplete.

### Token Telemetry

Frozen implementation Item 7 has not started. The Task Contract already contains a token budget, but canonical Token Telemetry is `NOT_IMPLEMENTED` until Item 7. ### Human notification

The failure reporter assigns the investigation issue to the repository owner and includes the workflow run, PR number, merge SHA and verification result. This provides a deterministic GitHub-native notification path. No separate SLA is invented by this task because no canonical SLA currently exists in its authorized scope.

## Lessons / precedent

- `GITHUB_TOKEN` recursive-trigger limitations must be considered when an Actions workflow itself performs a merge.
- Required post-merge evidence must be produced explicitly rather than inferred from pre-merge PASS.
- Exact immutable merge SHA is the verification target; a moving branch name is not evidence.
- Code verification should not share write-capable merge credentials when a separate least-privilege job is available.
- Post-merge failure is fail-visible and investigated; automatic rollback is not a safe default.
- Scope discipline remains mandatory even during repair cycles; recovery from an executor mistake must restore the authorized artifact before proceeding.
